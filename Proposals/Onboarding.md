# Proposals: 0002-onboarding

Modified: 2026-09-23

# Onboarding

This proposes how a silo with no configuration becomes a working server: a bootstrap mode that
a staged, then confirmed, pair of setup calls spends exactly once, a passkey that becomes the
operator's credential, recovery rooted in the server's own filesystem, and SiloAdmin — a macOS
console that discovers silos on the network, remembers the ones it has met, and walks a fresh
one through its first ten minutes. The paper contract, the on-disk formats, the operator routes and the approval model of
[0001-silo](Silo.md) all stand; this is about how the first operator gets through a door that
today only opens from inside the machine.

## The problem

A silo that has never been configured cannot be operated from the network. Every operator route
sits behind a bearer token; the token comes from `SILO_OPERATOR_TOKEN` in the silo's own
environment; and the node flow — a node asks, a person approves — presumes somebody was already
let in by some other means. Nothing approves the first approver. So a freshly started server,
with no operator token in its environment, serves reads to anyone on the network and refuses
every mutation to everyone, forever. The one way in is the host's own console: read logs, edit a
unit file, restart.

That is survivable for an operator who runs everything from a shell, and intolerable as the
first-run experience of a household appliance. Two things are missing. One is a door: a way for
the silo to accept its first operator credential over the network, once, and then never again.
The other is a counterparty: an application on the operator's machine that knows which silos
exist, which of them are waiting to be set up, and which it already has keys for. Today there is
no such application — `silo-ctl` assumes you already hold a token and already know an address.

## What this is

**A bootstrap mode.** A silo with no operator credential — nothing in its state directory and no
`SILO_OPERATOR_TOKEN` — boots as it always has, serving reads and refusing mutations, with one
addition: a setup pair. `POST /v1/setup` stages a passkey and a name in memory for ten minutes —
nothing written, dead on expiry or restart. `POST /v1/setup/confirm`, authenticated with the
staged passkey itself, is the write: the operator's credential installed, the silo named, and
bootstrap closed for good. The capability is spent exactly once per fresh server, by the
confirm, and cannot be reopened over the network; a stage that nobody confirms costs its ten
minutes and changes nothing.

**A passkey as the first credential.** The thing the confirmed setup installs is a random passkey —
128 bits, generated by the operator's device, shown to the operator once so it can live in a
password manager, and kept by the application that generated it. The silo stores only its
SHA-256, the same pattern it already uses for node secrets and tokens. After setup the passkey
*is* the operator bearer token: same routes, same gate, no second authentication concept.

**Recovery through the filesystem.** Console access to the silo's host is the household root of
trust — the pattern Emby's `passwordreset.txt` and Home Assistant's device console both use. A
lost passkey is regained by dropping a reset file into the silo's state directory, which the
next boot applies, deletes, and logs loudly. `SILO_OPERATOR_TOKEN`, when set, keeps its present
meaning and wins over anything in state, so a server run entirely from its environment behaves
just as it does today.

**SiloAdmin.** A macOS console that browses Bonjour, merges what it finds with a registry of
silos it has seen before, and shows the operator the truth in one glance: this silo is waiting
to be set up; this one is new to me; this one I have the passkey for; this one I've met but
can't get into (or can't into right now). For a bootstrap silo it runs the setup flow — mint the
passkey, show it once, offer to file it in the password manager, send it, remember the silo —
and for the rest it answers the everyday question, *what's out there and can I use it*.

## Principles

0001-silo's non-goals stand: not internet-facing, a household network, plaintext, one operator.
This proposal adds four principles of its own:

1. **The filesystem is the root of trust.** Anyone who can write the silo's state directory is
   the silo's owner; the network is not. Every recovery path bottoms out at the filesystem, and
   there is no network route that can re-open bootstrap on a configured server.
2. **A fresh server owes the network one spend and no more.** Everything an unauthenticated
   client can do to a bootstrap silo is enumerable in one sentence — stage a setup, and confirm
   a staged one with its own passkey. A stage is a ten-minute loan: repeatable, in-memory, and
   capable of changing nothing durable, because a client that never proves it kept the passkey
   must leave no trace. The capability itself is spent exactly once, by the first confirm.
   Jellyfin's re-forcible first-run wizard — an onboarding window that could be opened again
   with a crafted URL, letting a stranger re-take the admin account — is the cautionary tale
   this requirement is written against.
3. **Discovery is convenience; a URL is the mechanism.** Unchanged from 0001-silo. SiloAdmin
   works from Bonjour where Bonjour works, and from a typed address everywhere else; nothing it
   needs is unknowable from a URL.
4. **The passkey rarely travels.** It is generated off the server, and its install crossings of
   the network are exactly the setup pair — the stage's request body and the confirm's bearer,
   on plaintext, an accepted residual threat argued below. What the silo checks is a bearer, and
   what it stores is a hash.

## Vocabulary

- **ServerID** — a UUID the silo mints once, into its state directory, and keeps forever. The
  stable identity of a server, as against its name (set by the operator, changeable) and its
  address (a Bonjour browse away, or typed).
- **Bootstrap** — the silo's state while it holds no operator credential. A state, not a mode
  you put it in.
- **Staged setup** — a `POST /v1/setup` the silo has answered, with the passkey and name held
  in memory against a ten-minute deadline. Not a credential, not on disk, and not survivable
  by a restart.
- **Passkey** — the operator's first credential: 128 random bits, rendered for a human to file
  in a password manager. Not a WebAuthn passkey; that association is deliberate-deferral, argued
  under open questions.
- **Registry** — SiloAdmin's own memory: the silos it has seen, keyed by ServerID, with what it
  last knew of each.
- **Seen / unseen** — whether the registry knows a silo. A silo that is neither seen nor
  reachable does not exist, as far as SiloAdmin is concerned: nothing is known of it.
- **Access** — whether SiloAdmin holds a passkey the silo accepts, established by asking, not by
  looking in the Keychain.

## The server makes an identity for itself

A silo mints its ServerID at first boot and writes it to `server.json` in its state directory —
the same state directory that already holds `nodes/`, atomically written the same way. The file
also holds the silo's name: `SILO_NAME` when set, `Silo on <host name>` by default, and the name
setup gives it after that. The identity survives restarts, moves with the state directory, and
is never re-minted by anything but the operator deleting it — at which point the server is,
legitimately, a new server.

The identity is advertised and served. Bonjour's TXT records, which today carry `v=1`, gain
`id=<server-id>` and, while the server is in bootstrap, `b=1`; a configured server leaves `b`
absent. And the silo answers `GET /v1/server` with its id, its name, and whether it is in
bootstrap — an open route with nothing secret to give, so that a client pointed at a URL can
classify what it found without depending on Bonjour. Name, host and port were already discoverable;
id and bootstrap-state are the additions a machine client actually needs.

This is what makes SiloAdmin's registry decidable. A name is not an identity (the operator can
rename; two silos can share a name by accident), and an address is not an identity (DHCP is a
household fact). The ServerID is the key every other statement in this proposal indexes on.

## Bootstrap mode and the pair of calls it allows

Bootstrap is the empty case, not a launch flag: no `operator-credential.json` in the state
directory, and no `SILO_OPERATOR_TOKEN` in the environment. (The environment variable continues
to mean "the operator token is this", and takes precedence over anything in state when set —
today's deployments are a degenerate case that never enters bootstrap.) In bootstrap the silo
serves reads as it always has, refuses mutations as it always has, and answers two routes it did
not have:

```
POST /v1/setup
{ "name": "Living Room", "passkey": "…" }
→ 202   staged: ServerID, the name it would take, and confirmBy, ten minutes hence
→ 409   a setup is already staged and its window has not run out
→ 410   gone: the server is configured; this was only ever open in bootstrap

POST /v1/setup/confirm                Authorization: Bearer <the staged passkey>
→ 201   the silo's ServerInfo — id, final name, bootstrap now false
→ 401   a setup is staged, but not for that bearer
→ 404   nothing is staged — expired, restarted, or the server is configured
```

Staging is deliberately weightless: the passkey's hash and the name sit in memory against a
ten-minute deadline, and nothing is written until the confirm. The confirm is the write — the
SHA-256 of the passkey as the operator credential and the name, to the state directory
atomically — and the same write closes bootstrap: there is no flag to forget. A restart
therefore always opens a clean bootstrap, whatever was mid-staging when the process died, and
`operator-credential.json` only ever holds a confirmed credential.

The status codes are the design's spine. A setup staged while another is in flight gets `409`
and the window to wait out; the stager who disappears — crashed client, lost network, a minted
passkey never recorded — costs ten minutes of the operator's patience and no more, where a
one-call design would have bricked an unconfigured silo behind a credential nobody holds. A
confirm carrying the wrong bearer is a `401` that leaves the stage standing: a stranger's
guesses must not void the operator's pending setup. And a confirm sent a millisecond after a
successful one — this proposal deliberately includes the case, reviewed against the Jellyfin
wizard bug — finds nothing to confirm and gets `404`; the setup route itself answers `410` for
the rest of the server's life. The routes are documented in the OpenAPI document like every
other operation, since a door, even a one-shot one, should be specified rather than discovered.

The threat model does not change: the adversary is a guest on the household network, and the
setup pair — the stage's body and the confirm's bearer — crosses the network in plaintext. The
honest argument that this is acceptable is that every credential in this system — node secret,
node token, operator token — already crosses the same network in the same way, and this one's
unauthenticated crossings are these two and no more, under the operator's own timing. The
honest reading of what plaintext costs here is argued jointly with TLS under open questions.

Two things bootstrap does **not** bring with it. Open reads do not become closed reads: the
silo's media were always readable on the LAN and bootstrap changes nothing about that. And
setup does not seed libraries, transcoding profiles or anything else beyond identity and
credential: a configured silo with no libraries is a legal, useless, fixable state, and the
smallest setup that could work is the one specified. Seeding libraries belongs to a libraries
API that does not exist yet, and is listed under open questions.

## The passkey

The passkey is generated by the client that will use it — SiloAdmin on first contact, 128
random bits — and rendered for humans in transcribable groups, because its second home is a
password manager entry the operator files by hand if they wish. It looks like six groups of
letters and digits, not a sentence and not base64 soup; the exact rendering is SiloAdmin's own
decision and not part of the contract between client and server.

The contract is: the silo receives the passkey exactly once, hashes it, keeps `SHA-256(passkey)`,
and thereafter accepts the passkey as `Authorization: Bearer` on every operator route, on equal
footing with an environment-set token. Hash-only storage is the pattern `NodeStore` already
uses; this makes it do double duty for the operator's own credential. A fresh boot of a
configured silo loads the hash and authenticates against it — losing the silo's process never
loses the operator's access, which is the property that makes a password manager a sufficient
backup.

Why a passkey and not one of the alternatives that were considered:

- **A one-time code printed to the silo's log** would keep even that single plaintext crossing
  from happening, at the cost of making the first act of the supposedly-console-free flow a trip
  to the console — and on a containerised or remote-hosted silo, finding *the right logs* is
  precisely the skill this proposal exists to remove. The security it buys is real but narrower
  than it looks: a guest on the network who can reach the setup route in the seconds the
  operator takes to transcribe a code is an adversary the threat model has already conceded.
- **A PAKE or challenge-response scheme** would let the passkey never cross the network at all,
  and is the right answer for a server that faces the internet. For a household appliance it
  spends a cryptographic dependency and a client's worth of ceremony on a threat — passive
  sniffing of one packet, once — that sits outside the stated model.
- **A WebAuthn passkey proper**, device-bound in the Secure Enclave, is deferred rather than
  rejected, and is discussed under open questions together with the TLS it cannot sensibly live
  without.

## Recovery: the filesystem is root

The passkey is lost, or the silo's state directory has been restored from a backup that predates
setup, or the operator has simply decided the old passkey should die. Recovery is deliberate,
local, and loud:

- Drop `operator-credential.reset` into the silo's state directory. At boot, the silo reads a
  line of text from it — the new operator token — stores its hash as the operator credential,
  deletes the file, and logs the reset at a level nobody misses. An empty file logs and is
  ignored. This is Emby's `passwordreset.txt` translated into the silo's own state-directory
  vocabulary.
- Or set `SILO_OPERATOR_TOKEN`, which has always won, and restart. The environment remains the
  escape hatch of last and first resort, and this proposal is careful never to make a server's
  operator beholden to a file its environment could overrule.

Both paths leave evidence in the log. Neither is reachable from the network. Anyone who can do
either can already, today, read all the media the silo serves — the filesystem being the root of
trust is a description of what is true, not a power this proposal grants.

## SiloAdmin

SiloAdmin is a macOS application (SwiftUI) in this package, linking `SiloClient`, `SiloDiscovery`
and `SiloKit`. It is the console 0001-silo's operator never had, and its scope in this proposal
is deliberately narrow: discovery, the registry, and the setup flow. Approving nodes, scanning
libraries, watching jobs — the console it grows into — are follow-on proposals against the same
registry.

**Discovery and the registry.** SiloAdmin keeps a local registry of silos it has seen, keyed by
ServerID: the name it last used, the address it last answered at, when it was last seen, and
classification-relevant history. On launch it browses Bonjour and probes any typed-in addresses,
merging the results into the registry. Classification keys off the registry and the live probe,
not off discovery alone: a silo that is seen but unreachable right now renders with its
last-seen time and its last-known access state, rather than vanishing, because *the silo I had
keys for is offline* and *I never knew this silo* are different statements the operator needs
told apart.

**The classes.** Every silo SiloAdmin shows is exactly one of:

- **Bootstrap** — live advertisement or `/v1/server` says so. This silo is waiting for its
  operator, and gets the setup flow.
- **Unseen** — reachable, no registry entry. A silo SiloAdmin has never met: configured by
  someone, or some other console, or reset. The offered act is *claim*: enter the passkey from
  the password manager, let the app verify it, and the silo becomes seen-with-access.
- **Seen, has access** — registry entry, stored passkey, and the probe passes.
- **Seen, no access** — registry entry, but no passkey stored for this ServerID, or the probe
  fails: 401 from an operator route. The silo is known and the keys don't fit — someone rotated,
  or this isn't the machine that set it up. The offered act is to enter the passkey.

The probe is a real question, not inference: `GET /v1/nodes` with the stored passkey. 200 is
access, 401 is no access, unreachable is last-known-state. Asking is the only honest test —
anything less mistakes "we once set this up" for "the silo still accepts what we hold".

**The setup flow.** For a bootstrap silo, SiloAdmin generates the passkey, shows it in a sheet
that says *file this in your password manager; it's shown once*, offers to hand it to the
password manager or copy it, and — on confirmation — plays the pair in order: `POST /v1/setup`,
the passkey into its Keychain keyed by ServerID, then `POST /v1/setup/confirm` with the passkey
as bearer. The ordering is the point: the silo cannot become configured before the app holds
its own copy, so a crash mid-flow costs the stage its expiry and nothing more. A retry finds
the silo still in bootstrap and reuses the passkey the Keychain already holds for its ServerID
rather than minting afresh. A 409 says another console staged first, and shows the operator
the window being waited out. A 410 says someone finished first, and the silo becomes what the
probe says it is. The passkey is stored in the Keychain and nowhere else, is never logged, and
the one display of it is the one time SiloAdmin ever renders it in full.

## What this looks like to the operator

A new box is switched on. SiloAdmin, wherever it is already running, notices within a browse
interval: a silo, waiting to be set up. Click through, see the passkey, file it, confirm — the
silo names itself, closes its door behind it, and moves to *seen, has access*. Nothing else
changes hands.

Six months later the Mac is replaced. The silo reappears as *seen, no access* — no registry, no
keys. The operator files the silo's passkey from the password manager, the probe passes, and the
console is whole again. Only when both are lost — machine and password manager — does the door
require the filesystem, which is the correct place for a lost-everything recovery to require.

## What this asks of an implementation

Each step is a pull request, in order, and each carries its spec deltas into `openspec/` per the
corpus README — the deltas are written now, under [`specs/`](Onboarding/specs/) beside this
proposal.

### 1. The server's identity and its own route

`server.json` in the state dir (ServerID, name), minted at first boot and loaded after; the
documented `GET /v1/server` answering id, name and bootstrap; Bonjour TXT gains `id` and, while
in bootstrap, `b=1`. The operator credential moves from env-var-only to env-var-then-state-file
(`operator-credential.json`, hash only), so bootstrap is a computable state: neither present.

Tests: identity survives a restart and a rename; `/v1/server` answers before and after setup;
TXT carries `id` always and `b=1` only in bootstrap.

### 2. The setup pair and its one spend

`POST /v1/setup` (`SetupRequest` → staged reply: ServerID, name, `confirmBy`) and
`POST /v1/setup/confirm` (bearer-authenticated → `ServerInfo`) in the document and served in
bootstrap. Staging lives in memory against a ten-minute deadline and writes nothing; the
confirm lands the credential hash and name in state atomically and closes bootstrap. The reset
file: `operator-credential.reset` in the state directory applied at boot, deleted, logged loud.
`SILO_OPERATOR_TOKEN` precedence over state preserved and tested.

Tests: a stage expires on schedule and survives no restart — a boot from mid-stage opens a
clean bootstrap with no credential file; a second stage inside the window is 409; the wrong
confirm bearer is 401 and the stage stands; confirm, then setup is 410 and confirm 404, and
both hold after a restart; the reset file rotates the credential and is consumed; the
environment variable wins over state; reads and node registration behave identically before
and after setup.

### 3. SiloAdmin

The `SiloAdmin` target: Bonjour browse merged into a persisted registry keyed by ServerID; the
four classes and the `GET /v1/nodes` probe; the setup sheet with its shown-once passkey and
Keychain storage; claim-by-passkey for unseen and lost-access silos. macOS-only, in a package
whose server side stays cross-platform — the target is declared for macOS and the existing
products are untouched.

Tests: classification of silos across the seen/reachable/access matrix; the registry survives an
app restart; setup reclassifies bootstrap to seen-with-access, a 410 lands in the probe's
verdict, and an interrupted setup resumes on the Keychain's passkey.

## Non-goals

- **TLS, and everything that wants it.** Transport security is a separate change with its own
  server-side consequences (certificates, identity of clients) and is argued under open
  questions, jointly with WebAuthn.
- **Multiple operators, roles, users.** The passkey is a second face of the one operator
  credential, not the first of several. 0001-silo's single-operator model stands.
- **Internet onboarding.** Remote setup, e-mail flows, claiming against a cloud service — the
  Plex shape. This proposal goes out of its way to need no server but the one being set up.
- **SiloAdmin as the whole console.** Approving nodes and running operations from the Mac are
  follow-on proposals; this one establishes the registry they will all key off.
- **Library and profile configuration at setup.** Listed under open questions because it has
  users pushing both ways, not because it was overlooked.

## Open questions

1. **TLS, jointly with WebAuthn.** Plaintext is accepted for exactly one crossing the passkey
   ever makes, and refused as a reason to design around WebAuthn later. If and when the silo
   grows a hostname and certificate management — the genuine prerequisite — the pair should be
   taken together: TLS makes the channel honest, WebAuthn makes the credential device-bound, and
   neither half is worth the dependency alone on a household LAN. Plex demonstrates the
   cloud-mediated version of this (`*.plex.direct`), and its price — onboarding that phones a
   vendor — is the one this system is designed against.
2. **Libraries at setup.** Setup could take initial libraries, which means the operator
   typing host paths into a Mac app for a box in the cupboard — or libraries grow their own
   operator routes (`POST /v1/libraries`) and SiloAdmin's console phase does it properly. This
   proposal suspects the latter and says so rather than half-saying the former.
3. **The passkey's spoken form.** Groups of characters, a word list, or both; how it is offered
   to the password managers that matter (1Password's import, Keychain's). SiloAdmin's
   implementation detail, but a real one: the day this is mistyped is the day recovery matters.
4. **Several operator credentials.** Rotation and revocation are one credential deep today. If a
   second human ever operates the silo, named operator identities — rather than a shared
   passkey — would be the fix, and would deserve their own proposal.
